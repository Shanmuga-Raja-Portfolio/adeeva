## Confirmed findings

### T1: Slow trailing-slash regex on the URL hash (Low, fixed)

- **Where:** `src/studio/studioRoute.ts`, `parseRoute`, which runs on every render with `window.location.hash`.
- **Problem:** `hash.replace(/\/+$/, "")` backtracks. On a hash of many slashes that does not end in a slash, the work grows with the square of the length.
- **Who could trigger it:** anyone who sends a link. A link like `/#/` + 200,000 slashes + `x` freezes the tab before the studio settles. No data is exposed and reloading without the hash recovers, so this is a nuisance, not a breach.
- **Evidence:**
  - **Node, regex alone:** 48 ms at 10,000 slashes, 193 ms at 20,000, 755 ms at 40,000.
  - **Running preview, crafted link opened with Playwright:**
    - WebKit (the engine on iPhone and iPad): 4.7 s at 100,000 slashes, 19.0 s at 200,000.
    - Chromium: 16 ms. Its regex engine handles this pattern, which is why Strix's Chromium browser could not see the problem.
- **Fix at the root:** the hash is trimmed with a plain loop (`routePath`), which takes linear time. The regex is gone.
- **Test:** `studioRoute.test.ts` "reads a crafted hash of many slashes in linear time". It parses three 200,000-slash hashes and must finish within 500 ms. Against the old code the test fails (18.9 s); with the fix it passes.
- **After the fix:** the same 200,000-slash link settles in 54 ms in WebKit and 18 ms in Chromium on the rebuilt preview. No other source regex has this shape (`/x+$/` or `/x*$/` on input).

### T2: One malformed request crashes `vite preview` (Info, preview only, upstream)

- **Where:** Vite 8.3.4's preview server (`connect` → `parseurl` → `url.parse`), before any of our middleware runs.
- **Problem:** the single request line `GET http://[ HTTP/1.1` makes Node throw `ERR_INVALID_URL` outside any `try`, and the `vite preview` process exits. Reproduced on port 6224 during triage. This also briefly interrupted the Strix run, which recovered after a restart.
- **Impact:** none for the shipped site, which Cloudflare Pages serves. Locally it kills the preview, which matters only when the preview listens on the LAN (`--host 0.0.0.0`, needed for Docker scans).
- **Why no fix in our code:** our `hostHeaders` middleware never sees the request, so wrapping its `new URL(...)` (O110's suggestion) would change nothing.
- **Upstream status:** no Vite advisory covers it. Vite 8.3.4 is the latest release.
- **Mitigation:** bind the preview to `127.0.0.1` unless a scanner in Docker needs it, and stop it after the scan, as this run did. Worth reporting to Vite privately.
